Create OAuth Apps For Integrations [#create-oauth-apps-for-integrations]

This guide is for workspace admins and operators who need to create OAuth apps for Aptlystar integrations. It focuses on the practical setup work: what app to create in each provider, what values to copy out of that provider, and which Aptlystar environment variables those values belong in.

> This page covers user-consent OAuth integrations. Google service accounts use a different flow. See `google-service-account.mdx`.

What You Need From Each Provider [#what-you-need-from-each-provider]

For almost every OAuth integration, you need to collect these values from the provider portal:

* `client id`
* `client secret`
* registered redirect URI or callback URL
* approved scopes or permissions
* sometimes an app review or publish step before the integration works for non-admin users

The main exception in the current codebase is `trello`, which uses an API key instead of a client ID and client secret pair.

How Redirect URIs Work In Aptlystar [#how-redirect-uris-work-in-aptlystar]

Most integrations use this redirect URI pattern:

```txt
${NEXT_PUBLIC_APP_URL}/api/auth/oauth2/callback/{provider-id}
```

Special cases:

* `shopify` uses `/api/auth/oauth2/callback/shopify`
* `trello` uses `/api/auth/trello/callback`

Always register the public browser-facing URL, not `INTERNAL_API_BASE_URL` or any internal cluster URL.

Keep these two app env vars aligned for each environment:

```bash
BETTER_AUTH_URL=<public app origin>
NEXT_PUBLIC_APP_URL=<public app origin>
```

Environment Examples [#environment-examples]

Use your real public domain for each environment:

| Environment | Example public origin         | Required app env                         |
| ----------- | ----------------------------- | ---------------------------------------- |
| Local       | `http://localhost:3000`       | `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL` |
| Test        | `https://staging.example.com` | `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL` |
| Production  | `https://app.example.com`     | `BETTER_AUTH_URL`, `NEXT_PUBLIC_APP_URL` |

If a provider lets you register multiple redirect URIs in one OAuth app, you can usually use one provider app for local, test, and production. If a provider only allows one redirect URI, create one provider app per environment.

The Basic Workflow [#the-basic-workflow]

1. Pick the provider you want to enable in Aptlystar.
2. Create an OAuth app in that provider's developer portal.
3. Add the Aptlystar redirect URI for local, test, and production.
4. Copy the client ID, client secret, or API key into the matching Aptlystar env vars.
5. Restart the app, then test the connection in `Settings -> Integrations`.

Provider Groups At A Glance [#provider-groups-at-a-glance]

Some Aptlystar integrations share one provider app:

* Google: Gmail, Calendar, Drive, Docs, Sheets, Contacts, Forms, Ads, BigQuery, Vault, Groups, Meet, Tasks, Vertex AI
* Microsoft: Teams, Excel, Dataverse, Planner, Outlook, OneDrive, SharePoint, Microsoft Ads
* Atlassian: Confluence and Jira are separate registrations in the current codebase

The rest are usually one provider app per integration.

Shared Provider Apps [#shared-provider-apps]

Google Cloud [#google-cloud]

**Covers**

* Gmail
* Google Calendar
* Google Drive
* Google Docs
* Google Sheets
* Google Contacts
* Google Forms
* Google Ads
* BigQuery
* Google Vault
* Google Groups
* Google Meet
* Google Tasks
* Vertex AI

**Collect from Google**

* client ID
* client secret

**Set in Aptlystar**

```bash
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
```

**Redirect URIs to register**

* `/api/auth/oauth2/callback/google-email`
* `/api/auth/oauth2/callback/google-calendar`
* `/api/auth/oauth2/callback/google-drive`
* `/api/auth/oauth2/callback/google-docs`
* `/api/auth/oauth2/callback/google-sheets`
* `/api/auth/oauth2/callback/google-contacts`
* `/api/auth/oauth2/callback/google-forms`
* `/api/auth/oauth2/callback/google-ads`
* `/api/auth/oauth2/callback/google-bigquery`
* `/api/auth/oauth2/callback/google-vault`
* `/api/auth/oauth2/callback/google-groups`
* `/api/auth/oauth2/callback/google-meet`
* `/api/auth/oauth2/callback/google-tasks`
* `/api/auth/oauth2/callback/vertex-ai`

**Steps**

1. Open Google Cloud Console and create or pick a project.
2. Open `APIs & Services` and configure the OAuth consent screen.
3. Enable the APIs you plan to use for each integration you will connect.
4. On the OAuth consent screen, add the **Scopes by Google service** listed below for every Aptlystar integration you enable (users only see consent for scopes you add here).
5. Open `Credentials` and create an `OAuth client ID` for a web application.
6. Add the Aptlystar redirect URIs above for local, test, and production.
7. Copy the `client ID` and `client secret` into `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.

**Scopes by Google service**

Aptlystar requests these scopes per callback (`apps/aptlystar/lib/oauth/oauth.ts`). Register the matching Google APIs and add equivalent scopes on the consent screen.

**Notes**

* Aptlystar requests offline access and stores refresh tokens.
* If scopes change in a release, update the consent screen and re-verify the app when required by Google.

Microsoft Entra ID [#microsoft-entra-id]

**Covers**

* Microsoft Ads
* Microsoft Teams
* Microsoft Excel
* Microsoft Dataverse
* Microsoft Planner
* Outlook
* OneDrive
* SharePoint

**Collect from Microsoft**

* application/client ID
* client secret

**Set in Aptlystar**

```bash
MICROSOFT_CLIENT_ID=
MICROSOFT_CLIENT_SECRET=
```

**Redirect URIs to register**

* `/api/auth/oauth2/callback/microsoft-ad`
* `/api/auth/oauth2/callback/microsoft-teams`
* `/api/auth/oauth2/callback/microsoft-excel`
* `/api/auth/oauth2/callback/microsoft-dataverse`
* `/api/auth/oauth2/callback/microsoft-planner`
* `/api/auth/oauth2/callback/outlook`
* `/api/auth/oauth2/callback/onedrive`
* `/api/auth/oauth2/callback/sharepoint`

**Steps**

1. Open Microsoft Entra ID and go to `App registrations`.
2. Create a `New registration`.
3. Under `Supported account types`, choose `Accounts in any organizational directory and personal Microsoft accounts` if you want the app registration to allow both work/school accounts and personal Microsoft accounts.
4. Add a `Web` redirect URI for each Aptlystar callback you need.
5. Open `Certificates & secrets` and create a new client secret.
6. Open `API permissions` → `Add a permission` → `Microsoft Graph` → **Delegated permissions**. Add every scope Aptlystar requests for the integrations you enable (see **Delegated scopes by Aptlystar callback**). For Dataverse, also add **Dynamics CRM** delegated permission `user_impersonation` (shown as `https://dynamics.microsoft.com/user_impersonation` in OAuth). Grant admin consent for the tenant when required.
7. Copy the `Application (client) ID` and the generated secret into `MICROSOFT_CLIENT_ID` and `MICROSOFT_CLIENT_SECRET`.

Source: `apps/aptlystar/lib/oauth/oauth.ts`. Use the Microsoft Graph permission names below in Entra (add `offline_access` for refresh tokens).

| `microsoft-teams`     | `openid` `profile` `email` `User.Read` `Chat.Read` `Chat.ReadWrite` `Chat.ReadBasic` `ChatMessage.Send` `Channel.ReadBasic.All` `ChannelMessage.Send` `ChannelMessage.Read.All` `ChannelMessage.ReadWrite` `ChannelMember.Read.All` `Group.Read.All` `Group.ReadWrite.All` `Team.ReadBasic.All` `TeamMember.Read.All` `offline_access` `Files.Read` `Sites.Read.All` |

* Even with a multi-tenant + personal app registration, not every Aptlystar Microsoft integration is practical for personal Microsoft accounts.
* `outlook`, `onedrive`, and `microsoft-excel` are the most likely to work with personal accounts.
* `microsoft-ad`, `microsoft-teams`, `sharepoint`, `microsoft-planner`, and `microsoft-dataverse` are typically work or school account integrations because they depend on org or tenant-level Microsoft Graph and Dataverse permissions.

Validation Checklist [#validation-checklist]

* `BETTER_AUTH_URL` and `NEXT_PUBLIC_APP_URL` match the real public origin
* all required redirect URIs are registered in the provider app
* the client ID, client secret, or API key is stored in the correct Aptlystar env var
* the provider app has the scopes Aptlystar expects
* the integration can be connected from `Settings -> Integrations`
* token refresh or reconnect works after the initial connection
